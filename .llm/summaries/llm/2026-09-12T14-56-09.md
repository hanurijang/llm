# 대화 요약

## 사용자의 목표/요청
- **`.service`(systemd)에 API 키가 있었는데 `/etc/env/.env`가 아니었던 것 같다 → 두 곳에서 관리해야 하나?** 라는 의문 제기
- 이어서 **"현재(저장소) 폴더에 `.env`를 만들어 관리하면 안 되나?"** 요청
- 근본 목표: DeepSeek API 키를 **한 곳에서만 관리**하고, systemd(.service) 쪽 키와의 혼동을 해소

## 결정 사항과 이유
- **`DEEPSEEK_API_KEY`는 실제로 `/etc/env/.env` 한 곳에만 존재**. systemd의 키는 `fastapi.service` 14행의 `CLIENT_API_KEYS`로 **성격이 다른(raspApi 클라이언트 인증) 키**이며 DeepSeek와 무관(전수 검색으로 확정).
- **키 관리 위치를 저장소 폴더 `.env`로 통일**(권장). 조회 순서를 `LLM_ENV_FILE` → **저장소 `.env`** → `/etc/env/.env`(시스템 공용 폴백)로 정의, **앞이 우선**(이미 설정된 환경변수는 덮어쓰지 않음).
- `.gitignore`에 `.env`가 있어 **커밋/push되지 않음** → 키 유출 방지, 새 PC에서는 한 번 재생성 필요.
- `--yes` 배너에서 `SHELL_ASK_SOURCES[ask_source]` **KeyError** 발견 → **CLI 옵션 출처는 안내문이 없으므로 `.get()`으로 방어**. (환경변수 출처일 때만 안내 출력)

## 생성/수정된 파일과 핵심 코드 변경

  - `load_dotenv(*paths: Path) -> list[Path]`로 재작성: `LLM_ENV_FILE` → 인자 경로(기본 저장소 `.env` → `/etc/env/.env`) 순서로 로드, 이미 있는 키는 유지, 실제 읽은 경로 목록 반환. `export KEY=` 접두 처리.
  - `print_banner`의 `SHELL_ASK_SOURCES[ask_source]` → `.get(ask_source)` + 존재 시에만 출력.
  - 에러 메시지에 저장소 `.env` 언급 추가.
- **`llm`(bash 래퍼)**
  - `load_env_file()` 함수 도입: `LLM_ENV_FILE` → `$DIR/.env` → `/etc/env/.env` 순서로 로드, 기존 변수는 유지. 주석·공백·따옴표 처리, `export ` 접두, 키 형식 검증.
